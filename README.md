# SM TAP — кабинет цифровых визиток

Клиент может зарегистрироваться, заполнить свою анкету и после сохранения отправить SM TAP постоянную ссылку для записи на NFC. Также один аккаунт SM TAP может управлять несколькими визитками клиентов. Сотрудник входит со своей почтой и паролем, создаёт анкету клиента, заполняет её и записывает постоянную ссылку /p/<id> на NFC-карту. Почта и пароль клиента не требуются. Посетители открывают опубликованные анкеты без регистрации.

## Использование

1. Войти в свой аккаунт на главной странице. Регистрация нужна один раз для владельца кабинета.
2. Нажать «Новая визитка», указать имя, контакты и при желании фото. Email в анкете необязателен.
3. Подтвердить право на публикацию данных и нажать «Создать визитку».
4. Скопировать постоянную ссылку и записать её на NFC-карту.
5. Для изменения контактов выбрать клиента в списке, внести изменения и сохранить. Адрес остаётся прежним.

Список можно искать по имени и описанию. Скрытие и удаление касаются только выбранной анкеты. Удаление требует подтверждения и текущей версии записи. Скачивание и импорт JSON работают для выбранной визитки. При смене анкеты редактор предупреждает о несохранённых изменениях.

Визитки принадлежат аккаунту, который их создал. Другие аккаунты не получают к ним доступ. Миграция снимает ограничение уникальности owner_id, сохраняет все прежние записи, их версии и NFC-адреса, добавляет индекс для списка владельца.

## Разработка и размещение

Серверное приложение Vinext / Cloudflare Workers с D1. Авторизация — существующий Firebase Authentication, защищённые HttpOnly Secure cookies. Публичные страницы не требуют входа. Репозиторий хранится в Sites, проект указан в .openai/hosting.json; существующая публичная аудитория сохраняется.

API /api/profile: GET без id возвращает компактный список только своего аккаунта; GET с id открывает одну анкету; POST с id обновляет выбранную, без id и с revision=0 создаёт новую; DELETE требует id и revision. Владелец всегда берётся из серверной сессии. Проверяются Origin, формат, размер, поля и версия записи.

## Проверки

node node_modules/typescript/bin/tsc --noEmit

node tests/security.mjs

Production-сборка выполняется стандартным build-site.mjs. Тесты используют настоящий локальный D1 и имитацию границы аутентификации. Проверяют сохранность старых данных при миграции, несколько анкет в одном кабинете без клиентской почты, изоляцию аккаунтов, постоянные адреса, отдельное удаление, CSRF, конфликты версий, ограничения и vCard. Реальная авторизация Firebase и NFC на физическом телефоне требуют пользовательской проверки.

## Сборка из архива

Версия Sites 4, коммит 39e753f6b6b03f6b0f1d63228e59f46df624d3de.
В этой копии встроенный ключ Firebase вынесен в переменную Worker
FIREBASE_WEB_API_KEY. Для локального запуска укажите её в файле .dev.vars
(значение Web API Key берётся из настроек вашего проекта Firebase).
В Firebase Authentication должен быть включён вход по email и паролю.

Нужны Node.js 22.13+ и pnpm 11.25.0 из package.json (при выборе версии Node
учтите также требования установленного pnpm). Из корня проекта выполните

```sh
pnpm install --frozen-lockfile
pnpm run build
```

Сборка создаёт dist/server/wrangler.json из vite.config.ts и .openai/hosting.json.
В репозитории отдельного wrangler.toml или wrangler.jsonc нет.
Для первого запуска с пустой локальной D1 примените схему по порядку

```sh
for migration in drizzle/[0-9]*.sql; do
  pnpm exec wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file "$migration" || exit 1
done
pnpm start
```

Для локального Worker передайте FIREBASE_WEB_API_KEY через .dev.vars рядом
с используемым Wrangler-конфигом (для pnpm start это dist/server/.dev.vars).
Для разработки с Vite используйте pnpm dev.

## Развёртывание в собственном аккаунте Cloudflare

Для отдельной установки войдите через Wrangler и создайте пустую базу

```sh
pnpm exec wrangler login
pnpm exec wrangler d1 create sm-tap-cards
```

В vite.config.ts замените тестовые database_id и database_name данными созданной
базы, сохранив binding DB. Пересоберите через pnpm run build. Проверьте в
dist/server/wrangler.json имя Worker для отдельной установки и привязку базы.
Для новой пустой базы примените исходные SQL-миграции один раз

```sh
for migration in drizzle/[0-9]*.sql; do
  pnpm exec wrangler d1 execute DB --remote --config dist/server/wrangler.json --file "$migration" || exit 1
done
pnpm exec wrangler deploy --config dist/server/wrangler.json
pnpm exec wrangler secret put FIREBASE_WEB_API_KEY --config dist/server/wrangler.json
```

Последняя команда запросит ключ интерактивно. Для уже существующей базы
сначала сверьте применённые миграции. Архив содержит схему и историю изменений.
Клиентские анкеты и учётные записи в него не входят.
